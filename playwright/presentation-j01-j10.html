Playwright : de l’authentification au diagnostic

Un parcours en dix étapes pour structurer les tests d’une application, exercer ses parcours clients et rendre les échecs exploitables.

Cadre

Vue d’ensemble

Le projet organise des tests de parcours, de contrôle d’accès et de comportement UI face à des réponses API contrôlées. Les étiquettes J01 à J10 désignent des étapes du parcours, pas des dates de réalisation vérifiées.

10étapes thématiques
3projets de test : admin, user, chromium
4sorties de reporting : liste, HTML, JSON, JUnit

Organisation

  • Configuration & environnement
  • Pages & composants
  • Fixtures & sessions
  • Tests UI / API / mocks
  • Rapports & triage

Le projet setup prépare les sessions utilisées par admin et user. Le projet chromium exécute les scénarios du répertoire UI. Les tests nécessitent une application accessible et des comptes de test configurés.

J01
Fondations

Architecture et parcours de connexion

Poser une structure lisible et vérifier un premier parcours utilisateur de bout en bout.

Organisation du code

Les scénarios Gherkin vivent dans features/, leurs étapes Playwright dans steps/, les objets de page dans pages/ et les éléments partagés dans components/. La configuration se trouve dans playwright.config.ts et les paramètres sensibles sont chargés depuis l’environnement.

Parcours vérifié

Ouverture de la connexion, saisie des identifiants, contrôle de l’URL et du titre du tableau de bord, puis déconnexion et retour à la page de login.

Sources : Test de connexionLoginPageVariables d’environnement

J02
Modélisation

Page Object Model et création client

Centraliser les interactions avec les pages pour garder les scénarios métier compréhensibles.

LoginPage, DashboardPage et ClientPage encapsulent les actions utilisées par le test : se connecter, accéder aux clients et créer un enregistrement. Le nom du client combine l’index du worker et l’horodatage pour limiter les collisions ; le scénario vérifie ensuite sa présence dans la liste.

Portée. Le test exerce une création réelle sur l’application configurée : prévoir un environnement et des données de test adaptés.

Sources : Scénario de créationClientPageDashboardPage

J03
Réutilisation

Une fixture de page authentifiée

La fixture personnalisée authenticatedPage étend le test Playwright : elle ouvre la page de connexion, effectue le login avec le compte configuré, puis fournit la page au scénario via use(page). Le test du tableau de bord peut ainsi se concentrer sur son assertion.

Cette fixture effectue une connexion UI ; elle est distincte du mécanisme de sessions enregistrées introduit pour les rôles.

Sources : FixtureTest du tableau de bord

J04
Contrôle d’accès

Rôles et réutilisation des sessions

Séparer les attentes ADMIN et USER et éviter de répéter la connexion dans chaque scénario de rôle.

  1. Le projet setup connecte chaque rôle par l’interface et enregistre son storageState dans .auth/.
  2. Les projets admin et user dépendent de ce setup et chargent l’état associé.
  3. ADMIN accède au tableau de bord et à Clients ; USER ne voit pas le module dans la navigation et ne peut pas l’ouvrir directement selon les assertions des tests.
Attention aux secrets. Les états d’authentification et identifiants sont sensibles ; les conserver hors du versionnement et utiliser des comptes de test.

Sources : Setup des rôlesAccès ADMINAccès USER

J05
Interaction

Upload et aperçu du logo

Dans le dialogue d’ajout de client, le test injecte un PNG en mémoire avec setInputFiles, puis vérifie que l’image d’aperçu est visible et que son attribut src est une data URL PNG. Il attend ensuite quatre secondes et annule le dialogue : le scénario ne crée pas de client.

Cette attente fixe existe dans le test ; une attente liée à un état observable serait une piste d’amélioration si elle répond au besoin métier.

Source : Test d’interaction complexe

J06
API + interface

Connexion API et reprise côté UI

Relier l’identité obtenue par API à une navigation authentifiée dans l’interface.

  1. Partir d’un stockage vide, ouvrir /login et attendre le jeton CSRF dans sessionStorage.
  2. Effectuer le login API avec ce jeton, puis appeler /users/me avec l’access token et comparer l’email au compte attendu.
  3. Installer le cookie et les éléments de session nécessaires dans le navigateur, puis ouvrir /clients et vérifier le titre « Gestion des clients ».

Ce scénario teste l’intégration réelle avec l’API et l’application configurées ; il ne se limite pas à une réponse simulée.

Sources : Scénario API / UIClient d’authentification API

J07
Isolation réseau

Mocks des réponses clients

Les routes Playwright interceptent l’API clients pour vérifier la réaction de l’interface, sans dépendre de la réponse réelle de cet endpoint. Les tests vérifient également que les requêtes ont bien été interceptées.

Cas simuléComportement vérifié
200Le client et sa ville apparaissent dans la liste.
400Affichage de « Aucun client trouvé ».
401 + refresh 401Retour à la connexion, après interception des deux requêtes.
500Affichage de l’état vide.
TimeoutRequête interrompue avec abort('timedout') ; état vide vérifié.

Ces contrôles décrivent le comportement actuellement attendu par les tests, pas nécessairement le traitement idéal de chaque erreur.

Source : Scénarios de mocks

J08
Paramétrisation

Dix cas pilotés par les données

Le fichier JSON contient dix clients. Le plan du scénario Gherkin reprend ces dix cas dans une table d’exemples et génère un test distinct par entrée ; chaque cas construit une réponse API simulée et vérifie le titre, le nom, la ville et le pays affichés, ainsi que l’interception de la requête.

Cette approche élargit la variété des données tout en gardant un scénario commun. Elle vérifie l’affichage de données simulées, et non la création ou la persistance de dix clients réels. La table d’exemples et le JSON doivent rester cohérents.

Sources : Jeu de donnéesScénarios paramétrés

J09
Fiabilité

Latence, attentes et retries

Observer la synchronisation face à une latence variable, sans confondre une relance réussie avec une exécution stable.

Scénario

La réponse clients simulée est retardée aléatoirement jusqu’à 500 ms. Après navigation, expect(...).toBeVisible() attend l’apparition du client : l’attente porte sur le résultat observable plutôt que sur une durée fixe côté test.

Politique de retry

La configuration prévoit 2 retries en CI et 0 en local. Un test qui échoue puis réussit au retry est suivi séparément comme flaky dans les KPI.

Protocole des 20 essais

npm run test:j09 -- --repeat-each=20 --retries=0

Compter les réussites et échecs dans le rapport de cette exécution, puis conserver le rapport JSON et les traces pertinentes. Désactiver les retries rend visibles les échecs de chaque répétition ; le setup et l’environnement restent des dépendances du parcours.

Mesures réalisées pendant l’exercice. La lecture immédiate a échoué 20 fois sur 20 avec une latence allant jusqu’à 2,2 secondes. Après une première correction, des échecs persistaient ; avec une latence réduite à 500 ms et un worker, 20 répétitions ont réussi. Les conditions ayant changé, cela ne prouve pas à lui seul que toute la suite est stable.

J10
Observabilité

Traces, rapports et triage

Faire d’un échec une enquête reproductible, avec des preuves et des hypothèses clairement distinguées.

Nature du test J10

Il s’agit d’un test de diagnostic positif avec réponse API 200 simulée. Trois test.step ouvrent la liste, joignent la réponse JSON au rapport et vérifient l’affichage de « QA Diagnostic Client ». Ce n’est ni un test d’échec volontaire, ni un appel réel à l’API clients.

Artefacts Playwright

La configuration conserve trace et vidéo en cas d’échec et prend une capture en cas d’échec. Les reporters produisent une liste console, un rapport HTML, un JSON et un JUnit.

Triage

report:failures produit un classement initial des échecs ; une analyse des traces, du réseau et des données est nécessaire pour confirmer la cause. Les timeouts sont ambigus.

npm run test:j10
npm run report:failures
npm run report:kpi
npx playwright show-report playwright-report
npx playwright show-trace chemin/vers/trace.zip

Les scripts de reporting exploitent les résultats JSON disponibles : leur portée est celle du run qui les a produits, pas nécessairement celle de toute la suite.

Bilan et perspectives

Ce que le projet couvre

  • Parcours UI structurés en objets de page et fixtures.
  • Sessions par rôle et articulation API / navigateur.
  • Cas réseau simulés, données paramétrées et diagnostic instrumenté.
  • Rapports exploitables et classification initiale des échecs.

Prochaines étapes

  • Conserver les résultats des répétitions J09 et comparer les exécutions.
  • Réduire les attentes fixes et isoler les données créées.
  • Compléter les contrôles d’erreur et confirmer les causes avec les traces.
  • Calibrer les KPI sur une référence représentative et suivre les limites de couverture.
Prudence sur le statut. Cette présentation décrit le code et son intention. Les tags J01 à J10 représentent une progression pédagogique, pas des dates de réalisation attestées ; les résultats dépendent du run, de l’environnement, des comptes et des données disponibles.
